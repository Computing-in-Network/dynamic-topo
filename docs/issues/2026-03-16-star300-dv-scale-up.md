# Route A DV 从 100 节点继续扩展到 300 节点

## 背景

当前仓库已经完成：

- 10 节点 Route A DV 原型
- 50 节点稳定性验证
- 100 节点规模验证

现在需要继续增加节点规模，并在每一级规模上做一致的可重复验证，直到：

1. 成功推进到 300 节点
2. 或在某个规模上验证失败，从而明确当前实现的规模上限

## 目标

1. 将 Route A DV 场景从 `100` 节点继续向上扩展
2. 以统一流程验证 `100+` 规模，逐级扩大直到无法继续通过
3. 自动记录每一级规模的启动状态、路由收敛和端到端可达性
4. 如果瞬时拓扑连通但持续动态更新后子集失连，需要明确指出原因

## 范围

1. 新增 scale-up 自动化脚本
   - 逐级启动指定规模的 Route A DV 场景
   - 自动设置合适的运行目录与路由超时参数
   - 自动检查 agent 数量、路由条数、端到端 ping

2. README 补充
   - 如何使用 scale-up 脚本
   - 如何查看每一级规模的验证结果

3. 执行验证
   - 至少覆盖 `110+`
   - 明确每一级是否通过
   - 明确最终可稳定推进到的上限

## 验收标准

1. 自动化脚本能够按顺序启动多个规模场景
2. 每一级输出以下结果：
   - agent 存活数
   - node1 路由数
   - nodeN 路由数
   - node1 -> nodeN ping 是否成功
3. 最终输出：
   - 通过的最大节点规模
   - 若失败，给出失败规模和观测现象

## 注意事项

1. scale-up 过程不能与静态控制面并行运行
2. 不同规模的运行目录、日志和映射文件必须隔离
3. 300 节点若失败，不代表系统完全不可用，而是当前 DV 原型实现达到规模边界

## 本轮结论

1. 已新增“按实时拓扑采样最大连通分量并抽取连通子图”的扩容逻辑
2. 已验证 `110` 节点可以从瞬时连通分量中启动，并能在真实子集端点间形成可达路径
3. 但 `110` 节点在持续动态更新下不能保持整个子集长期全连通：
   - 瞬时采样可得到 `best_component_size=131` 或更高
   - 实际连续运行后，`run/star110_dv_route_a/dv_neighbor_snapshot.json` 显示该 110 节点子集会分裂成多个连通分量，最大仅 `100`
4. 因此当前 Route A DV 原型在“实时动态拓扑持续更新 + 全子集保持可达”的严格标准下，仍只能稳妥宣称 `100` 节点通过
5. 若要继续推进到 `110+ / 300`，需要先改变验证方法或系统行为，二选一：
   - 冻结拓扑后做规模上探
   - 改成基于多帧稳定核心节点集合选子图，而不是基于单帧最大连通分量选子图
